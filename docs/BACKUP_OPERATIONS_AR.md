# تشغيل النسخ الاحتياطية واستعادة البيانات

تعمل مهمة GitHub Actions المسماة **Encrypted database backup** يوميًا الساعة **03:23 UTC**، ويمكن تشغيلها يدويًا من صفحة Actions. تُحفظ النسخ اليومية 30 يومًا، ونسخة يوم الأحد 90 يومًا. قد يتأخر التنفيذ المجدول لدى GitHub؛ راجع نتيجة المهمة ووجود الملف، وليس الموعد وحده.

## ما الذي تحتويه النسخة؟

تحتوي على بيانات جداول التطبيق في مخطط `public`، بما فيها تاريخ الأعضاء، الملاحظات الخاصة، الإعدادات السرية، سجلات المزامنة والجداول القديمة وحقولها الإضافية مثل `owner_user_id`. تشمل تعريف الأعمدة والقيم الافتراضية والتسلسلات والقيود والفهارس والدوال والمحفزات وسياسات RLS والصلاحيات. لا تُنسخ محتويات جداول أجزاء النسخ الاحتياطية نفسها.

يأخذ الخادم أقفال قراءة مشتركة على الجداول بترتيب ثابت، ثم ينسخ البيانات داخل معاملة واحدة. عند وجود كتابة متزامنة تمنع القفل، يعيد المحاولة بدل إنتاج نسخة مختلطة. تُنقل البيانات على أجزاء صغيرة مع SHA-256، ثم تُضغط وتُشفّر بـ **AES-256-GCM**. الملف المرفوع الوحيد ينتهي بـ `.brawlbackup` ولا يحتوي بيانات مكشوفة.

يمنع الترحيل `028` بدء لقطة جديدة أثناء وجود مزامنة جارية، ويؤجل بدء المزامنة عندما تكون اللقطة قيد الإنشاء. تنتهي الحماية عند اكتمال التقاط البيانات؛ تنزيل الأجزاء والتشفير والرفع لا يحتفظ بأقفال الجداول. تظل إعادة تنزيل لقطة موجودة وقراءة نتيجة مزامنة مكتملة ممكنتين.

يحاول عميل النسخ الطلب نفسه خمس مرات كحد أقصى، بفواصل انتظار 1 ثم 2 ثم 4 ثم 8 ثوانٍ، أي 15 ثانية انتظار إجمالًا إضافة إلى زمن الطلبات. إذا استمرت المزامنة أو المنافسة أكثر من هذه المهلة فقد تفشل المهمة مؤقتًا؛ أعد تشغيلها بعد انتهاء العملية الجارية. لا تُشغّل الصيانة عند فشل التصدير، ولا تتغير مواعيد المزامنة أو النسخ تلقائيًا.

هذه نسخة **للتطبيق**، وليست نسخة كاملة من منصة Supabase: لا تشمل حسابات Supabase Auth، كلمات مرور المستخدمين، ملفات Storage أو بيانات المخططات المدارة مثل `auth` و`storage` و`vault`. تُسجل الإضافات المثبتة، لكن تُطلب عند الاستعادة فقط الإضافات المرتبطة بكائنات التطبيق. إذا أصبح جدول أو سياسة أو دالة يعتمد على مخطط خارجي أو إضافة غير متاحة، فقد تتوقف تجربة الاستعادة حتى تُوفّر التبعية الصحيحة. لا تُنشأ بدائل وهمية لـ `auth.uid()` أو `auth.role()` لإخفاء المشكلة.

## حفظ المفتاح ومراقبة المهمة

احفظ نسخة آمنة ومستقلة من سر GitHub المسمى `BACKUP_ENCRYPTION_KEY` في مدير كلمات مرور أو خزنة مشفرة. هو مفتاح عشوائي من 32 بايت بصيغة Base64. **فقدان المفتاح يعني عدم إمكانية فك النسخ**؛ GitHub لا يعرض قيمة السر بعد حفظه. عند تدوير المفتاح، احتفظ بالمفاتيح القديمة مع تواريخ استخدامها حتى انتهاء الحاجة إلى النسخ القديمة. لا تضفه إلى Git أو ملف مرفوع أو سجل تشغيل.

السران `VERCEL_APP_URL` و`CRON_SECRET` يتيحان التصدير من التطبيق. لا يحتاج التصدير إلى كلمة مرور قاعدة Supabase. الوصول إلى واجهة النسخ متاح للمسؤول أو لرمز الجدولة، وجداول النسخ غير متاحة لمفتاح `anon` أو دور `authenticated`.

بعد التصدير تُجرّب الاستعادة في PostgreSQL محلي معزول وفارغ، وتُقارن أعداد الصفوف وبصماتها وتُفحص الصلاحيات. يُرفع الملف المشفر حتى إن فشلت تجربة الاستعادة، ليبقى مصدرًا للتعافي. لا تُؤكَّد النسخة ولا تُشغَّل صيانة الحذف إلا بعد نجاح الاستعادة والرفع معًا. عند الفشل تبقى أجزاء النسخة الخاصة قابلة لإعادة التصدير لمدة 24 ساعة؛ تُنظّف الأجزاء المنتهية عند إنشاء النسخة التالية.

## استرجاع ملف بعد عطل

من GitHub افتح Actions، ثم المهمة، ثم شغّلًا ناجح التصدير، وحمّل الأثر `database-backup-<RUN_ID>`. يمكن استخدام GitHub CLI أيضًا، بعد استبدال رقم التشغيل والمسار:

```powershell
gh run list --workflow backup.yml
gh run download RUN_ID --name database-backup-RUN_ID --dir 'C:\private-recovery\encrypted'
```

احتفظ بنسخة إضافية خارج GitHub إذا أردت مدة أطول من سياسة الاحتفاظ. الملف المشفر قابل للاستعادة حتى لو تعطل التطبيق أو فُقد مشروع Supabase، طالما بقي المفتاح والملف وكود أداة الاستعادة.

## تجربة الاستعادة الآمنة

من مجلد المشروع نفّذ `npm ci`. في نافذة طرفية أولى شغّل قاعدة الاختبار المحلية:

```powershell
node scripts/start-test-db.cjs
```

في نافذة ثانية، أدخل المفتاح دون إظهاره، ثم نفّذ الاستعادة إلى قاعدة الاختبار الفارغة التي أُنشئت للتو:

```powershell
$backupKey = Read-Host 'Backup encryption key (Base64)' -AsSecureString
$env:BACKUP_ENCRYPTION_KEY = [System.Net.NetworkCredential]::new('', $backupKey).Password
$env:RESTORE_DATABASE_URL = 'postgresql://postgres:local-test-only@127.0.0.1:55432/brawl_backup_tests'
node scripts/restore-backup.cjs 'C:\private-recovery\encrypted\database.brawlbackup' --apply
Remove-Item Env:BACKUP_ENCRYPTION_KEY
```

تتحقق الأداة من سلامة التشفير قبل تنفيذ أي SQL. ترفض عنوانًا خارجيًا أو قاعدة غير فارغة أو ترميزًا غير UTF8، وتسمح فقط بأسماء محلية من شكل `brawl_*_tests` أو `brawl_*_restore`. لا تحذف قاعدة موجودة لتجاوز الرفض؛ أنشئ قاعدة اختبار جديدة. نتيجة `verified: true` تعني تطابق كل الصفوف وفحص صلاحيات الملاحظات والإعدادات والدوال الخاصة. أي فشل أثناء إنشاء المخطط أو تحميل البيانات يُلغي معاملة الاستعادة.

للمراجعة الإضافية يمكن تنفيذ الاستعلامات التالية في قاعدة الاستعادة المحلية؛ القيم المتوقعة بالترتيب هي `false` و`true` و`false`:

```sql
SELECT has_column_privilege('anon','public.member_history','notes','SELECT');
SELECT has_column_privilege('anon','public.member_history','player_tag','SELECT');
SELECT has_table_privilege('authenticated','public.member_reviews','SELECT');
```

راجع البيانات والصلاحيات محليًا قبل إعداد خطة نقل إلى الإنتاج. أداة الاستعادة هذه ترفض الإنتاج عمدًا؛ نقل البيانات إلى مشروع حي يحتاج إجراءً منفصلًا ونسخة أمان مسبقة. كما أن النسخ الجديدة لا تعيد تاريخًا مُسح قبل أول نسخة؛ يلزم مصدر أقدم لاستعادة ذلك التاريخ.
