# تشغيل المزامنة المتدرجة

يستدعي Supabase Cron المسار `/api/sync?mode=auto` كل دقيقتين. يجلب الفحص الخفيف قائمة النادي بطلب لعبة واحد. عندما يحين التحديث الكامل، يجلب أيضًا ملفات اللاعبين ومعاركهم كل 10 دقائق، ويطلب الرتب كل 30 دقيقة. تظهر أوقات اكتمال هذه المصادر بصورة مستقلة في لوحة التحكم.

## التثبيت والتحويل

1. احفظ نسخة مشفرة واختبر استعادتها في قاعدة محلية فارغة.
2. طبّق ترحيلَي `202609160005_adaptive_sync.sql` و`202609160006_upstream_cooldowns.sql` بعد الترحيلات السابقة، ثم انشر التطبيق.
3. نفّذ `supabase/operations/enable_adaptive_scheduler.sql` من محرر SQL بصلاحيات مالك المشروع. يستخدم رمز `scheduler_token` الخاص الموجود أصلًا؛ لا تضع الرمز في نص مهمة cron.
4. تحقّق من طلبَي HTTP تلقائيين ناجحين ومن سجلات `sync_runs` المقابلة. نجاح `cron.job_run_details` يعني إدراج الطلب في الطابور؛ لا يكفي وحده لإثبات اكتمال المزامنة.
5. بعد نجاح التحقق، أزل جدولة المزامنة والتسليم القديمة من GitHub وVercel. احتفظ بتشغيل GitHub اليدوي للتشخيص، وبمهمة النسخ الاحتياطي اليومية.

مهمة الإشعارات تعمل كل دقيقتين في الدقائق المتناوبة، وتُرسل طلب HTTP فقط عند وجود إشعارات مستحقة. تتبع تفعيل Discord المحفوظ. تُحفظ سجلات cron الخاصة بهذه المهام سبعة أيام.

## الحماية والبيانات

- المزامنة الخفيفة والكاملة والفردية تستخدم القفل نفسه ومعاملة حفظ محمية؛ لا تستطيع عمليتان تطبيق تغييرات متعارضة. يُعاد استخدام نطاق الطلب الأصلي عند تكرار مفتاح الطلب بعد اكتماله.
- الفحص الخفيف يحفظ العضوية والاسم والرتبة داخل النادي والكؤوس والأيقونة. يحافظ على تفاصيل اللاعب والمعارك والرتب التنافسية والبراولرز الموجودة.
- يُحفظ النشاط عند تغيّر الكؤوس، ومعه عينة أساس كل 30 دقيقة في غياب التغير. لا تُعدّل صفوف المعارك والبراولرز اليومية غير المتغيرة. تبقى أحداث العضوية التاريخية مستقلة ودائمة.
- فشل المعارك أو الرتب لا يتحول إلى بيانات جديدة أو وقت نجاح زائف. تبقى آخر محاولة كاملة وتحذيراتها ظاهرة حتى بعد نجاح فحوص النادي التالية.
- تُحترم ترويسة `Retry-After`، مع إعادة محاولات محدودة وتأخير متزايد وعشوائي. تُحفظ مهلة كل مصدر في قاعدة البيانات لتلتزم بها نُسخ الخادم الأخرى. لا تتجاوز العملية ميزانيتها الزمنية لانتظار مهلة طويلة.
- عند ظهور بيانات فعلية جديدة، تتجدد الصفحات المفتوحة من خلال فحص حالة مشترك كل 30 ثانية وعند العودة للتبويب. هذا لا يجعل مصدر اللعبة يرسل أحداثًا مباشرة.

لـ28 عضوًا، المتوقع دون إعادة محاولات نحو 8,784 طلب لعبة يوميًا عند فحص النادي كل دقيقتين والكامل كل 10 دقائق، ونحو 1,344 طلب رتب يوميًا. تختلف الأرقام عند الفشل أو التشغيل اليدوي. تظل حصص التخزين ونقل البيانات وقيود مقدمي الخدمات سارية؛ لا يحتاج هذا التصميم اشتراكًا إضافيًا لتفعيله في المشروع الحالي.

## الإيقاف المؤقت والاستعادة

لإيقاف إدراج الطلبات الجديدة دون حذف إعداداتها، غيّر قيمة `sync_scheduler_enabled` إلى `false` باستخدام صلاحيات الإدارة. لا يلغي ذلك طلبًا دخل الطابور بالفعل. لإعادة التشغيل، أعدها إلى `true`.

النسخ المشفرة تشمل بيانات التطبيق ودواله الخاصة. إعدادات `cron.job` وداخلية `net` موارد مُدارة خارج مخطط `public`؛ يعيد ملف التشغيل أعلاه إنشاء مهامها عند الانتقال إلى مشروع Supabase جديد. تظل الدوال المستعادة خاملة في اختبار PostgreSQL المحلي، ولا تنشئ مهام إرسال أو مزامنة تلقائيًا.
